283-badminton-app リファクタリング監査レポート

2026-07-25 / 対象: v3.6.0 時点の dev/release / 調査: 6 観点並列監査 (API 設計・フロントエンド構造・パフォーマンス・UI/UX・データモデル・テスト/依存関係)

結論サマリー: 発見 62 件を統合・重複排除して 36 項目 に整理。
  • S (緊急 5 件): セキュリティ穴 1、本番障害リスク 3、情報漏洩 1。v4.0.0 を待たず hotfix 推奨
  • A (v4.0.0 の柱 10 件): 全 API の共通化、race condition 解消、LINE WebView 非互換 UI の一掃、DB 負荷対策
  • B (v4.0.0 に同梱可 13 件): フロント構造整理、UX 統一、テスト補強
  • C (スコープ外提案 8 件): 大規模アーキテクチャ変更・依存メジャーアップグレード
横断的な根本原因は 3 つ: ① middleware.ts 不在 → 認証ガードが全 25 ページ + 53 API ファイルにコピペ ② LINE WebView 対応部品 (Select / ConfirmModal) を作ったのに、旧実装 (native select / confirm()) が大量に残存 ③ ActivityLog 等の無制限成長 + インデックス欠落が 5 DTU の Azure SQL Basic に蓄積ダメージ

S: 緊急対応 (v4.0.0 を待たず hotfix 推奨)

IDタイトル問題改善案リスク規模
S1 SECCRON エンドポイントの認証バイパス /api/cron/remind は CRON_SECRET が未設定だと認証チェックを完全スキップ。誰でも全参加者への LINE 通知を発射でき、月 200 通のフリー枠も枯渇させられる if (!secret || auth !== ...) に修正し「未設定 = エラー」へ。あわせて本番 env の設定有無を確認 高小
S2 BUGユーザー削除が本番で FK エラーになる SQL Server 側は PointTransaction / AchievementUnlock / AnnouncementRead が NoAction、Event.createdById が Restrict のため、イベント作成歴・ポイント履歴のあるユーザーの削除 (承認却下含む) が DB エラーで失敗しうる 削除ルートに 3 テーブルの deleteMany を追加 (トランザクション内)。Event.createdBy は SetNull 化 or 削除時付け替え 高中
S3 CI本番 db push の失敗が黙殺される PROD パイプラインの prisma db push が continue-on-error: true。schema 適用失敗でも新コードがデプロイされ、コードと DB の不整合状態で本番が動く continue-on-error を外し、失敗時はデプロイを止める (or 通知必須化) 高小
S4 PERFDB インデックス 3 本の欠落 最頻クエリがインデックスに乗っていない: ① Event.eventDate (イベント一覧) ② Attendance.eventId (イベント詳細) ③ ActivityLog.createdAt (analytics)。5 DTU では全件スキャンが直撃 両 schema に @@index 3 本追加。db push だけで適用でき、コード変更・ユーザー影響ゼロ 低 (改善効果 高)小
S5 SECエラーレスポンスで内部情報漏洩 43 箇所で message: String(error) を返しており、Prisma のテーブル名・カラム名・制約名がクライアントに露出 本番では汎用メッセージに統一、詳細は console.error のみ (A1 の共通ヘルパーとセットで対応可) 中小

A: v4.0.0 の柱 (構造改善・体感改善が大きい)

IDタイトル問題改善案リスク規模
A1 ARCHAPI 共通ヘルパー導入 (withAuth / apiError) 認証チェックが 53 ファイル 77 箇所にコピペ。try-catch 無しルート 12 件は DB エラーが素の 500 HTML になる。エラー形式も不統一 withAuth(handler, {require}) + apiError(code) を新設し全ルートを移行。S5 も同時解決。挙動は不変なのでユーザー影響なし 低大
A2 BUG出欠登録 + 繰り上げの race condition 解消 定員チェック→登録→キャンセル待ち繰り上げがトランザクション外。同時操作で「定員超過」「同 position 重複」「二重繰り上げ」が起こり得る (コア機能の整合性問題) attendance 登録〜promoteFromWaitlist を $transaction で包む。invite/complete・settings PUT・メンバー削除も同様に整備 中中
A3 UXconfirm() / alert() の全廃 → ConfirmModal 統一 20 箇所超が native confirm()、エラーも alert() 混在。LINE WebView の一部環境では confirm() が即 false を返し、削除・LINE 通知確認などが操作不能または確認スキップになる恐れ 既存の ConfirmModal に順次置換、エラーはインライン赤バナーに統一 高 (現状の方が危険)大
A4 UXnative <select> の全廃 → 自前 Select 統一 Android LINE WebView 対策で自前 Select を作ったのに、EventForm (8 箇所)・承認カード・管理画面などで native select が残存。Android ユーザーが操作できない可能性が残っている 全 native select を Select コンポーネントに置換 (計 17 箇所) 高 (現状の方が危険)大
A5 PERFイベント一覧 API の軽量化 (_count 化) 一覧が全イベントの全出欠レコードを include (30 イベント × 50 人 = 1500 行を毎回転送・集計)。最頻アクセス画面で DTU を浪費 Prisma の _count + 自分の分だけの where 絞りに書き換え。転送量ほぼゼロに 中 (要リグレッション確認)大
A6 PERFActivityLog / AttendanceHistory のパージ戦略 全 API が書き込む ActivityLog が無制限成長。Azure SQL Basic は 2GB 上限であり、放置すると DB 停止リスク 90 日超のログを定期削除する cron (or 管理画面手動ボタン) を追加。保持期間はデータ活用方針と要相談 高 (放置した場合)中
A7 PERFanalytics API の DB 側集計化 ダッシュボードが 30 日分の ActivityLog を全件メモリに載せて JS 集計。ログ増加に比例して悪化 groupBy / raw query で DB 側集計に変更 低大
A8 DBスキーマ掃除 (Message 削除ほか) Message テーブルは Announcement 統合後コード参照ゼロの死にテーブル。schema コメントに observing 抜け、priorityScore の役割記述曖昧など文書化ズレも蓄積 Message + User.sentMessages を両 schema から削除、コメント修正。本番の既存レコード無を確認してから 低小
A9 DBcancelType 二重管理の整理 Attendance.cancelType (最新値) と AttendanceHistory.cancelType (履歴) の二重更新が必要な構造で、更新漏れ経路が生じうる (ポイント計算のズレに直結) 更新をヘルパー関数に集約してトランザクション化。二重更新漏れを構造的に防ぐ 中中
A10 ARCHzod バリデーション統一 7 ルートが手動 typeof チェックで、文字列長・空文字検証が抜けやすい zod スキーマ + safeParse に統一 (A1 とセットで実施すると効率的) 低小
